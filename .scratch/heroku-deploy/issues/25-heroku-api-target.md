# 25: Heroku API target

**What to build:** the production API running on Heroku at `https://api.majlis.elsaeed.dev`, backed by Heroku Postgres and Heroku Key-Value Store, with schema migrations applied on every release, so the Cloudflare Pages frontend can call it. The existing docker-compose stack keeps working untouched.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] `GET /health` returns 200 over a valid Heroku ACM certificate for `api.majlis.elsaeed.dev`
- [x] Every release applies the Alembic migrations; a failing migration blocks the release instead of booting a stale schema
- [x] The web process binds Heroku's `$PORT` and keeps idle connections alive long enough to avoid H13/H18 errors
- [x] CORS allows `https://majlis.elsaeed.dev` and `https://majlis-elsaeed.pages.dev`
- [x] Rate-limit buckets key on the client address Heroku appended, so a forged `X-Forwarded-For` cannot bypass signup/login limits and two clients never share a bucket
- [x] Redis is reached over TLS (`rediss://`); an unreachable Key-Value Store falls back in memory with a warning instead of blocking login
- [x] Postgres connects over SSL and stays under Essential-0's 20-connection ceiling with one web dyno plus release/one-off dynos
- [x] R2 accepts a browser preflight from the Pages origin for presigned PUT/GET/HEAD with the required headers
- [x] The compose stack still boots locally with no new required environment variables
- [x] ADR-0011 records Heroku's append semantics; ADR-0010 records the headers the API now emits itself

## Comments

- **2026-11-23 — delivered (agent):** Production API is live at `https://api.majlis.elsaeed.dev` on Heroku `majlis-elsaeed-api` (container stack, `eu`, Basic web dyno), backed by Postgres `essential-0` and Key-Value Store `mini`. Deployed commit `52ac3de`; release **v10** succeeded. Nothing is pushed to `origin` yet; local `main` holds the commit.
  - **Health + certificate:** `GET /health` → `200` `{"status":"ok"}` over HTTP/2 on both the custom domain and `…herokuapp.com`. ACM issued a Let's Encrypt certificate (`CN=api.majlis.elsaeed.dev`, SAN same, valid 2026‑11‑17 → 2027‑02‑15), confirmed with `openssl s_client`. The `api` record stays **grey-cloud** (DNS-only CNAME to the Heroku DNS target) — orange-clouding breaks ACM and ADR‑0011's `xff_rightmost` model.
  - **Migrations:** release phase ran `alembic upgrade head`; `alembic_version = b6419a8ca65a`, 14 app tables present. Gate proven with a throwaway branch (`tmp/failing-migration-probe`, commit `be58cb6`) whose `upgrade()` raised: release **v11** failed with `RuntimeError: ticket 25 probe: release phase must fail here` / `Process exited with status 1`, Heroku kept **v10** as Current and `/health` stayed `200` throughout. Branch deleted, `main` re-pushed (release succeeded).
  - **`$PORT` + keep-alive:** dyno command shows `--port 44658 --timeout-keep-alive 95 --timeout-graceful-shutdown 20`. Router 2.0 closes idle router↔dyno connections at **90 s** (the 55 s figure is the in-request data window), so 95 s lets the router always initiate the close. The earlier 75 s value was corrected after the spec review; no H13/H18 seen.
  - **CORS:** preflights from `https://majlis-elsaeed.pages.dev` and `https://majlis.elsaeed.dev` both return `200` with `access-control-allow-origin` set to the caller; a foreign origin returns `400` with no allow header. `FRONTEND_URL` + `CORS_ORIGINS` drive the list; trailing slashes are normalised and duplicates dropped.
  - **Rate limit:** 10 logins with rotating forged prefixes (`X-Forwarded-For: 203.0.113.N, 198.51.100.N`) → `401`×10, 11th → `429`; a 12th with a brand-new forged prefix → `429`; a duplicate-header request → `429`. The Redis bucket is `rl:/api/v1/auth/login:41.235.162.30` — the real client address the router appended, not any forged value. `_forwarded_chain` joins every `X-Forwarded-For` field before taking the rightmost entry (Router 2.0 combines duplicate fields per RFC 7230), so neither a forged prefix nor a second header can move the key.
  - **Redis:** attached URL is `rediss://`; PING succeeds (server 7.2.4) with `REDIS_SSL_CERT_REQS=none` (Heroku KVS presents a self-signed certificate) and 0.5 s connect/read timeouts. Fallback proven live: temporarily pointing `REDIS_URL` at an unreachable `rediss://127.0.0.1:6390` restarted the dyno, `/health` stayed `200`, logins returned `401` (never 5xx) and the in-memory window still tripped `429` on the 11th attempt; the URL was restored and re-verified byte-for-byte by PING plus a fresh limiter key written by the live app, so the app↔Redis path is healthy. The `logger.warning("Redis unavailable for rate limiting; using in-memory fallback.")` line itself scrolled out of Heroku's retained log window before it was captured; the behaviour is pinned by `test_rate_limit.py`.
  - **Postgres:** `pg_stat_ssl` shows every session on `TLSv1.3` (`sslmode=require` produced by `Settings.sync_database_url()` for Alembic and `ssl=require` for asyncpg). Pool is 4 + 2 overflow: a one-off dyno opened 12 concurrent holders and the server saw **7** sessions including the probe itself, i.e. 6 from the app — well inside the plan's 20-connection ceiling, with room for the release and `heroku run`.
  - **R2:** one bucket `majlis` (account `2bc0e70a…`), CORS rule as recorded in ADR‑0012. `OPTIONS` preflight from both production origins → `204` with `Access-Control-Allow-Origin`, methods `GET, HEAD, PUT` and the required headers; a foreign origin → `403`. End-to-end through `Aioboto3StorageClient`: presigned **PUT** `200`, **HEAD** exists with the right size, presigned **GET** `200` with matching bytes and `ETag, Accept-Ranges, Content-Range, Content-Length` exposed; the probe object was deleted afterwards. Note: the local `backend/.env` had a stale R2 endpoint (`d78030d1…`, auth denied) — corrected to the account endpoint and `S3_BUCKET=majlis`, which is now also the app/compose default.
  - **Compose untouched:** `docker compose -p majlis25 up` boots with no new required variable; `/health` `200` through nginx, SPA `200`, each ADR‑0010 header present exactly once (nginx hides the upstream copies). API startup ran `alembic upgrade head` as before.
  - **Two `heroku.yml` fixes found during the deploy:** a `release:` section needs `image: web` (otherwise Heroku rejects the push with "Couldn't find the release image configured for this app"), and `release.command` must be a single shell invocation — a multi-entry list is run as separate lines, so `[alembic, upgrade, head]` executed `alembic` alone and failed with "too few arguments". Both are recorded in ADR‑0012. Cosmetic: the slim image has no `curl`, so Heroku's release-log streaming helper falls back to plain output; release output is still visible in `heroku logs`.
  - **Quality gates:** `ruff` clean, `ty` clean, **211** backend tests passed on Postgres; `/code-review` run (Standards + Spec axes), findings fixed and re-verified.
